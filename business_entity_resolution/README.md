# DeepResolve ER: Business Entity Resolution System

A competition-grade, reproducible, modular Python system for cross-source Business Entity Resolution. Built for the ML Challenge 2026.

---

## 1. Problem Understanding
Modern commercial platforms aggregate business information from disparate, noisy sources. In this challenge, business records arrive from 3 sources:
- **Source 1**: Reference, deduplicated master source.
- **Source 2**: Noisy source.
- **Source 3**: Noisy source.

The objective is to map **every** Source 1 entity in the test set to **all** matching records in Source 2 and Source 3 that represent the same real-world business entity. A Source 1 entity may have **zero** matches (singletons), **one** match, or **multiple** matches.

## 3. Data Preprocessing & 4. Normalization
The preprocessing subsystem (`src/preprocessing/`) preserves original text while extracting normalized views:
- **Business Names**:
  - `original`: Unaltered raw string.
  - `cleaned`: Lowercase, accents stripped via Unicode NFKD, punctuation normalized.
  - `core_name`: Legal suffixes (Pvt Ltd, LLC, Inc, Corp, SARL, SAS, etc.) and prefixes (DBA, formerly, FKA) removed.
  - `tokens` & `sorted_tokens`: Word tokens and alphabetically sorted tokens for word-order invariance.
  - `char_ngrams`: Sub-word 3-grams.
- **Indic Transliteration**:
  - Offline phonetic matrix conversion for Devanagari and Gujarati scripts without external network lookups.
- **Addresses**:
  - Street abbreviation canonicalization (`st` $\to$ `street`, `rd` $\to$ `road`, `ave` $\to$ `avenue`, `ngr` $\to$ `nagar`, `r` $\to$ `rue`, etc.).
  - Country-aware postal code (5-digit / 6-digit PIN) and building number extraction.
  - Empty address safety mechanisms.

---

## 5. Candidate Generation & 6. Blocking Strategies
Comparing $1.73\text{M} \times 9.97\text{M} \approx 1.7 \times 10^{13}$ pairs is computationally infeasible. We execute a 4-way **UNION** candidate blocking engine strictly partitioned by country:
1. **Exact Name Blocker**: Exact match on `(country, core_name)`, `(country, sorted_tokens)`, `(country, alphanumeric)`.
2. **Token Inverted Index**: Retrieves records sharing discriminative business tokens ($\ge 4$ characters) with bounded posting lists.
3. **Sparse TF-IDF Retrieval**: Character 3-4 n-gram sublinear vectorization with sparse cosine matrix dot-product top-$K$ retrieval.
4. **Composite Address Blocker**: Matches on `(country, postal_code, name_prefix)` and `(country, building_num, street_token)`.

**Empirical Controlled Benchmark**:
- Exact Name Recall: 52.59%
- Token Index Recall: 82.28%
- TF-IDF Block Recall: 90.61%
- **UNION Recall**: **91.11%** (Average 31.7 candidate pairs per S1, 99.854% reduction ratio).

---

## 7. Feature Engineering
For every candidate pair passed to ML, 39 features are extracted:
- **14 Name Features**: Levenshtein similarity, Jaro-Winkler, Jaccard token similarity, character 3-gram Jaccard, token sort ratio, prefix similarity, common token count, length differences.
- **13 Address Features**: Address Levenshtein, token Jaccard, numeric token overlap, postal code match, building number match, empty flags.
- **7 Interaction Features**: $Lev_{name} \times Lev_{addr}$, harmonic mean of similarities, token agreement, $|Lev_{name} - Lev_{addr}|$, country agreement.
- **5 Provenance Features**: `gen_exact`, `gen_token`, `gen_tfidf`, `gen_address`, `gen_count`.

---

## 8. Training Pair Generation & 9. Hard-Negative Mining
- Positive pairs are constructed directly from `train_ground_truth.tsv`.
- Hard negative pairs are mined from candidates generated by the blocking stage that are not ground truth matches (e.g. similar names but different locations, or same address but distinct companies).
- Prevents the classifier from taking shortcuts on easy negatives.

---

## 10. Model Architecture & 11. Licenses
- **Model**: LightGBM Gradient Boosted Decision Tree (`LGBMClassifier`).
- **Hyperparameters**: `learning_rate=0.05`, `n_estimators=250`, `num_leaves=31`, `subsample=0.8`, `colsample_bytree=0.8`.
- **License**: LightGBM is released under the **MIT License**. All accompanying libraries (NumPy, SciPy, scikit-learn, RapidFuzz) are MIT/Apache 2.0/BSD compliant.
- **Parameter Count**: Tree ensemble contains ~150,000 parameters (well within the challenge's 8 Billion limit).

---

## 12. Validation Methodology & 13. Official Macro $F_{0.5}$ Evaluation
- **Zero Leakage Split**: S1 entities are split randomly by `entity_id` (not by pairs). A Source 1 entity never appears across both train and validation splits.
- **Official Macro $F_{0.5}$ Formula**:
  $$F_{0.5} = \frac{1.25 \times \text{Precision} \times \text{Recall}}{0.25 \times \text{Precision} + \text{Recall}}$$
- **Singletons**: An S1 entity with no true matches receives 1.0 for an empty prediction and 0.0 for any false merge.

---

## 14. Threshold Optimization & 15. Singleton / 16. Multi-Match Handling
- Grid search over decision thresholds $\tau \in [0.15, 0.85]$ directly optimizes macro $F_{0.5}$.
- The optimal threshold ($\tau^* \approx 0.44$) naturally balances precision against recall.
- Allows zero matches (singleton), one match, or many matches per entity without artificial 1-to-1 matching constraints.

---

## 17. Open-Set Country Generalization
- The training data includes `US` and `India`.
- The test set adds `France`.
- Country is treated as an open-set string label. The pipeline partitions indexing and candidate generation by country, automatically handling France without hardcoded assumptions.

---

## 18. Candidate-Pairs Methodology
`output/candidate_pairs.tsv` contains the exact candidate set evaluated by the ML model. The final matches in `output/matching_results.tsv` are mathematically guaranteed to be a strict subset of `candidate_pairs.tsv`.

---

## 19. Error Analysis
Diagnostic reports in `reports/error_analysis/` reveal:
- False positives occur primarily when distinct branches share the same corporate brand and partial address tokens.
- False negatives occur when extreme spelling corruption in both name and address reduces lexical overlap below blocking thresholds.

## 23. Computational Considerations & Memory Safety
- Uses chunked streaming loaders (`DataLoader`) to avoid loading 12.5M rows into memory simultaneously.
- Partitioning by country cuts memory requirements by 65%.
- Sparse matrix TF-IDF operations with top-$K$ pruning keep peak memory consumption $< 2.5$ GB.

---

## 24. Limitations
- Does not use external geocoding or business registry lookups (strictly compliant with fair-play rules).
- Completely novel foreign languages outside Latin and Indic scripts would require additional transliteration matrices.
